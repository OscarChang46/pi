# Agent 定义注册与能力路由草稿

状态：**DRAFT，待用户评审**。日期：2026-09-06。

本文是非规范性细化提案，不替代现行 Registry、Router 或 BND 文档，不修改代码和审批状态。

## 1. 当前事实与缺口

[装配入口](../../../../../../src/application/composition-root.ts)使用固定 Agent 标识和配置中的单一模型；[配置](../../../../../../src/config/runtime-settings.ts)提供模型、Prompt ID、预算和工具政策。当前没有已发布 AgentDefinition 的版本目录，也没有能力路由服务。

例如两个自定义 Agent 分别只读检索与文档总结，当前需由调用代码决定配置组合。目标是让调用者选择明确的 Agent 版本，或提交技术能力需求，由可解释的规则生成候选，再由 Run 受理冻结选择。

## 2. 所有权

| 组件 / 对象 | 权威内容 | 禁止职责 |
|---|---|---|
| AgentRegistry / AgentDefinition | 定义标识、不可变发布版本、发布与退役状态 | Run 生命周期、实时 Worker 健康、凭据 |
| CapabilityRouter / RouteProposal | 无持久权威状态；匹配结果及解释 | 创建 Run、冻结路由、业务优先级 |
| RunRegistry / RouteSnapshot | 本 Run 唯一冻结选择及相关版本引用 | 修改发布定义 |
| AdapterCapabilityPort | 版本化技术能力与健康观察 | 根据健康变化静默切换运行中模型 |
| Host 装配 | 逻辑执行配置到具体 Adapter/凭据句柄的绑定 | 将 SDK 实例写入定义或 Run DTO |

AgentDefinition 的 Persona 是技术指令描述，不是上层团队角色。Multi-agent 团队、成员、仲裁仍由业务编排拥有。

## 3. 定义版本建议

候选定义包含稳定名称与说明、能力声明、Prompt 版本引用、逻辑模型能力需求、工具能力范围和默认执行预算。具体字段与序列化格式待契约评审。

- 发布版本不可原地修改；修改 Prompt 内容也需要新的可追踪版本或不可变内容引用。
- 模型 Provider 的 SDK 类型、密钥和私有 Session 引用不能进入定义。
- 工具声明只是需求或权限上限，不是授权；真实调用仍通过 Security 判定和工具守卫。
- 动态健康属于观察快照，不写回定义版本。
- 退役只影响新的选择；历史 Run 仍可解析版本。紧急安全撤销走 Security，不借退役语义伪装权限撤销。

## 4. 候选操作表

正式职责来自 [AgentRegistry](../../../../../design/layers/l1-control/components/agent-registry.md)、[CapabilityRouter](../../../../../design/layers/l1-control/components/capability-router.md)及 [BND-L1-001](../../../../../design/contracts/bnd-l1-001.md)。下表仅细化操作语义。

| 操作 / 调用方 | 输入语义 | 输出语义 | 失败语义 |
|---|---|---|---|
| publish / 可信管理入口 | 定义提案、期望版本、稳定命令标识 | 已提交的不可变定义版本 | 同版本不同内容冲突；缺失必要引用拒绝 |
| retire / 可信管理入口 | 定义或版本引用、期望版本 | 新选择不可用的状态事实 | 幂等重复返回既有结果 |
| getVersion / Gateway、恢复逻辑 | 精确历史版本引用 | 只读描述 | 不用最新版本代替缺失历史版本 |
| listCandidates / Router | 能力约束、可见范围、数量上限 | 有界版本化候选 | 无匹配为空，不扩大权限 |
| observeCapabilities / Router | 逻辑 Adapter 能力引用、有效期要求 | 能力与健康观察快照 | 超时或过期标记不可用 |
| proposeRoute / Gateway | 冻结需求、定义候选、信封约束 | 有序 RouteProposal 及过滤理由 | 硬约束不满足时不降级 |
| acceptRoute / RunCommandPort 内部 | Proposal 及其版本证据 | 随 Run 提交的 RouteSnapshot | 校验失效则重新提案，不静默换模型 |

Registry 的持久化依赖独立 Definition Repository；变更与对应事件在同一聚合事务内提交，提交后通知缓存失效。

## 5. 首版匹配流程

1. 若请求显式指定 Agent 版本，验证该版本可用于新 Run，并验证必要能力和信封范围；不通过时直接拒绝。
2. 未指定时，按可见的已发布版本枚举有界候选。
3. 先过滤硬约束：工具能力、输入输出能力、预算范围、版本兼容、隔离要求。
4. 与 Host 编译的执行约束取交集；定义声明不能增加授权。
5. 使用已冻结的技术偏好排序，同分按稳定 Agent ID/版本键排序。
6. Proposal 带输入版本及过滤解释。Run 受理前重新验证关键版本，将选定结果写入自己的 RouteSnapshot。

首版不引入模型自动挑选 Agent、向量检索排名或学习式权重。技术排序应可在不调用模型的测试中复现。

## 6. 并发与失败

发布采用期望版本与幂等键：并发发布只能有一个版本提交成功，其余返回冲突，不覆盖历史。缓存只是加速，存储失败不能只更新内存。

定义退役与 Run 受理并发需要明确线性化规则：建议受理时重验版本可选性；提交后即固定该版本。后续退役不改既有 Run，安全撤销由执行前安全检查处理。

若底层存储无法保证退役/受理间所需的校验一致性，应在正式契约阶段明确受理凭证或版本条件，不能靠“先查后写”声称没有竞态；不要求 Definition 和 Run 共享巨型事务。

Provider 不可用时，已冻结 Run 由 Scheduler 决定等待、失败或显式新 Attempt 的恢复政策；不能由 Router 在背景替换 RouteSnapshot。更换模型可能改变成本与语义，需要单独受控策略。

## 7. 安全、容量与观测

- 发布入口仅允许可信管理路径；普通执行请求不能临时发布定义扩大工具集。
- 查询结果按主机提供的可见范围裁剪；不返回凭据、完整私有配置或敏感 Prompt 正文。
- 限制定义大小、版本总量、候选数量和能力观察超时；具体阈值在容量评审确定。
- 记录版本引用、候选数量、过滤原因与匹配时延；技术 ID 不直接作为高基数指标标签。
- 历史版本回收必须检查存活 Run、审计与恢复引用，不能按“退役即删除”处理。

## 8. 验收场景

- 同一冻结输入得到相同候选顺序和解释，不受 Map 插入顺序影响。
- 缺少必要能力时无候选，未产生虚假 Run 路由。
- 发布后修改原配置或 Prompt 不改变已发布版本。
- 发布冲突和相同命令重试不会产生重复版本。
- 退役版本不再参与新选择，历史 Run 可解析旧引用。
- 健康变化只影响新 Proposal，不替换运行中模型。
- Registry 与 Router 均不导入 Pi 原生类型、不实例化 Adapter。

## 9. 待评审决策

| 编号 | 建议默认 | 替代与取舍 |
|---|---|---|
| REG-01 | 首版优先显式 Agent 版本，能力路由为可选入口 | 所有请求自动路由较方便，但更难解释为何选择某个 Agent |
| REG-02 | 发布时绑定不可变 Prompt 内容引用 | 使用可变 Prompt ID 简单，但会破坏历史 Run 可复现性 |
| REG-03 | 硬约束过滤 + 稳定技术排序 | 动态评分更灵活，但需额外解释、质量评估和权重管理 |
| REG-04 | 模型不可用时保持原路由并报告，禁止静默降级 | 显式授权的替代模型策略提升可用性，但需新增语义与预算评审 |

## 10. 后续实施切片

先落地单个已发布 Agent 的精确版本查询与运行绑定，再加入发布/退役及历史引用；之后实现确定性候选路由，最后根据真实需求增加健康驱动的可选策略。无需修改 Pi 核心。
