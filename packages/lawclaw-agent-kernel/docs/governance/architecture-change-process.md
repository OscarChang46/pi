# LawClaw 架构设计变更标准流程

> 流程编号：`ACP-001`
> 版本：`1.0.0`
> 生效日期：`2026-09-02`
> 适用范围：总体架构、子系统边界、公开接口、权威数据、跨层依赖、安全与韧性策略、部署拓扑及其实现约束。

## 1. 目标与原则

本流程把架构变更从“口头约定”变成可定位、可评审、可验证、可回退的工程事实。任何架构变更都必须遵守以下原则：

1. **上层优先**：下层设计不得扩大或重新解释上层授予的职责。
2. **一个变更一个编号**：使用 `ACR-YYYY-NNNN`，设计决策使用 `ADR-NNNN`。
3. **先影响分析，后修改基线**：未批准的方案不得标记为当前架构。
4. **图、文、契约、代码、测试同步**：只修改其中一项视为未完成。
5. **默认不扩权**：边界不清、租户归属不清、安全策略缺失时停止实施。
6. **证据驱动验收**：批准只授权实施，验证通过并入基线后才代表变更完成。
7. **可逆优先**：必须说明回退点、兼容窗口和数据不可逆风险。

## 2. 何时必须走本流程

命中任一条件就必须创建 ACR：

- 新增、删除或移动子系统、组件、Port、Adapter 或 Composition Root 职责；
- 改变跨层调用、事件流、依赖方向或部署边界；
- 新增或修改公开接口、Schema、错误码、事件、状态机；
- 改变权威状态、投影、事务、租户或数据保留归属；
- 引入新的 Runtime、数据库、通信方式、工具类别、网络出口或 Secret 机制；
- 修改认证、授权、审批、安全默认值、恢复、幂等或一致性策略；
- 修改已锁定里程碑范围、顺序或验收门禁；
- 能力探针/Spike 可能被复用到生产，或验证结果会改变正式设计。

纯文字修正、失效链接修复和不改变语义的排版调整可以免 ACR，但提交说明必须标注 `architecture-impact: none`。

## 3. 变更级别

| 级别 | 判定 | 批准人 | 必需评审 |
|---|---|---|---|
| L0 文档修正 | 不改变任何架构语义 | 文档所有者 | 文档检查 |
| L1 组件内部 | 不改变公开契约、数据归属和跨层依赖 | 子系统所有者 | 架构、测试 |
| L2 边界变更 | 改变 Port、Schema、事件、数据或安全/韧性策略 | 总体架构所有者 | 架构、安全、数据、运维 |
| L3 总体变更 | 改变四子系统/运维/基础设施职责或允许依赖 | 总体架构所有者与业务负责人 | 全量评审及迁移方案 |

无法确定级别时按更高级处理。外部职责变化必须更新总体 Draw.io；仅 Kernel 内部实现变化使用 PlantUML，不修改总体 Draw.io。

## 4. 角色与职责

| 角色 | 职责 | 不得兼任的裁决 |
|---|---|---|
| 提议人 | 填写 ACR、备选方案、影响与回退 | 不得自行批准 L2/L3 |
| 子系统所有者 | 判断边界、接口、依赖和实施范围 | 不得忽略上层冲突 |
| 架构评审人 | 检查职责、依赖、DDD 边界和演进兼容 | 不替代安全/数据专项评审 |
| 安全/数据/运维评审人 | 分别检查租户、权限、数据、恢复与可观测性 | 不扩大业务职责 |
| 批准人 | 明确批准、拒绝或要求修改 | 不以口头默认代替状态记录 |
| 实施人 | 只实现已批准范围并提交验证证据 | 不得顺手扩大范围 |

同一人可承担多个角色，但 L2/L3 至少需要一名非实施人的复核；单人项目则必须保留完整自审清单和自动门禁证据。

## 5. 标准状态机

```text
DRAFT → IMPACT_ANALYZED → REVIEWED → APPROVED → IMPLEMENTING
      → VERIFIED → BASELINED → CLOSED

任意非终态可转为 REJECTED 或 ABORTED；
验证失败回到 IMPLEMENTING；范围变化回到 IMPACT_ANALYZED。
```

禁止从 `DRAFT` 直接进入实现。`APPROVED` 表示允许按批准范围实施；`BASELINED` 才表示图、文档、契约、代码和测试已经成为当前基线。

## 6. 八步执行流程

### 步骤 1：登记与分类（G0）

- 从模板创建 `docs/governance/changes/ACR-YYYY-NNNN-<slug>.md`；
- 写明触发原因、当前痛点、变更级别、提出人和目标确认人；
- 给出“明确不做”列表，避免范围自然膨胀；
- 在 `architecture-baseline.yaml` 的待处理项中登记编号。

### 步骤 2：边界与影响分析（G1）

必须逐项回答：

- 哪个子系统拥有该能力，哪些子系统明确不拥有；
- 对外 Port、方法、数据模型、错误码和事件是否变化；
- 权威状态、投影、事务和租户键归谁；
- 数据流、控制流、故障流和 OperationContext 如何传播；
- 是否新增依赖、循环依赖、Runtime 类型泄漏或 Composition Root 例外；
- 安全、韧性、容量、部署、回滚和兼容性影响；
- 哪些上层约束编号被实现、改变或冲突。

### 步骤 3：方案与决策（G2）

- 至少给出“建议方案”和“不扩权替代方案”；L2/L3 至少比较两个可行方案；
- 需要长期解释的选择创建 ADR；
- 更新候选 PlantUML；仅当外部职责变化时更新总体 Draw.io 候选版本；
- 给出契约/Schema 差异、迁移计划、兼容窗口与回退点；
- 定义可量化验收标准及质量波动预算。

### 步骤 4：专项评审与批准（G3）

- 架构评审检查职责和依赖；
- 安全评审检查默认拒绝、最小权限、租户和日志；
- 数据评审检查权威状态、事务、版本和迁移；
- 运维评审检查 Trace、指标、健康、容量和故障处置；
- 批准人在 ACR 中写明结论、时间、批准范围与附加条件。

涉及上层冲突时必须暂停，并按“冲突位置—原因—需要的新职责—不扩权替代方案”格式请求决定。没有明确批准，不得通过修改下层术语绕过冲突。

### 步骤 5：受控实施（G4）

- 建立 ACR 到需求、提交、文件、测试的追踪关系；
- 每个新增公开接口必须有完整中文契约：语义、前置条件、权限/租户、幂等、并发、超时/取消、错误、兼容性和可观测性；
- 实施中发现范围变化，立即停止并把 ACR 状态退回 `IMPACT_ANALYZED`；
- 能力探针/Spike 必须显式隔离，默认不能被生产 Composition Root 引用。

### 步骤 6：验证（G5）

最低门禁：

- 上层约束追踪覆盖率 100%；
- 图、文档、Schema、代码职责映射一致；
- 循环依赖、禁止依赖、具体 Runtime 类型泄漏均为 0；
- 公共接口中文契约覆盖率 100%；
- 跨租户负向测试、工具越权测试和日志泄漏检查通过；
- 无界循环、队列、Buffer、输出和重试为 0；
- 变更前后关键质量指标在批准的波动预算内；
- 回退演练或可验证的回退步骤完成。

### 步骤 7：并入基线

- 把 ACR 状态改为 `BASELINED`；
- 更新 `architecture-baseline.yaml` 的当前基线、已批准变更和产物哈希/版本；
- 把候选图替换为正式图，确认 Markdown 引用可用；
- 归档测试、安全、迁移和兼容性证据；
- 若对外职责没有变化，在 ACR 中明确记录“总体 Draw.io 无需变更”。

### 步骤 8：关闭与复盘

- 兼容窗口结束、迁移完成后标记 `CLOSED`；
- 记录实际收益、意外成本、遗留项和是否需要反向决策；
- 未完成项必须另建 ACR/任务，不得藏在已关闭变更里。

## 7. 质量波动预算

每个 ACR 必须选择并填写适用指标的基线值、阈值和证据：

| 维度 | 默认门禁 |
|---|---|
| 职责漂移 | 新增未授权职责 0 |
| 依赖健康 | 循环依赖 0，禁止依赖 0 |
| 契约兼容 | 未声明 breaking change 0 |
| 多租户 | 跨租户负向用例 100% 通过 |
| 安全 | Secret/Prompt/正文/工具参数日志泄漏 0 |
| 韧性 | 无限重试、无界队列和无界输出 0 |
| 正确性 | 受影响测试 100% 通过 |
| 性能 | p95 延迟/内存退化默认不超过 10%，否则需专项批准 |
| 可观测性 | 新路径关键 Span、错误码和耗时指标覆盖 100% |

## 8. 能力探针规则

能力探针可以减少生产级持久化、部署和兼容性工作，但不能绕过职责和安全边界：

- 必须有 ACR，状态至少为 `APPROVED`；
- 必须写明验证假设、退出条件和禁止进入生产的隔离方式；
- 可以使用内存状态和 Faux Provider，但必须保留正式 Port；
- 真实模型只在调用方显式提供 SecretHandle/环境变量时启用；
- 能力探针验证成功不自动批准生产化，生产化必须重新评审数据、部署和运维能力。

## 9. 紧急变更

只有正在发生的安全事件或生产中断可以走紧急路径。紧急路径允许先实施最小止血，但必须：

1. 记录负责人、时间、影响和回退命令；
2. 不扩大权限，不关闭租户隔离，不写入明文 Secret；
3. 24 小时内补 ACR 和证据；
4. 3 个工作日内完成正式评审、基线化或回退。
