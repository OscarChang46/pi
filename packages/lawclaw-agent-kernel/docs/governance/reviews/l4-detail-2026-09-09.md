## 关键设计阻塞与解决路径

- B1：新版 plan.limits 已传数值限额，但完整 Sandbox 档案与 Security 绑定尚需联合冻结。上游生产、Guard 验证和 L4 解析必须使用同一不可变约束。
- B2：查询 DTO 冲突已由新版 BND-L34 收敛；剩余为 L1/宿主对原 locator、结果、lateFactSink 与 Artifact pin 的可靠交接验收，不能凭 L4 Promise 返回宣称已保存。
- B3：选定满足硬限额、启动屏障、原子创建标签、执行树停止和清理的机制档案，冻结 supervisor 帧 Schema及明确容量/时间配置。阻塞不可信执行。
- B4：每个 Provider 声明可信效果来源、查询能力；提供 scope 私有 mapping/receipt 及保留装配。无可信证据返回 unknown。

这些是明确的跨组件或机制集成工作，不用开发默认值关闭。单进程只读 Provider 和纯 collector 可继续细化/评审；整层不宣称已可生产集成。

## 当前实现对照

已读取现有 ToolExecutor、SandboxPlanner、ReadOnlyToolProvider、InProcessReadOnlySandbox 与 tool-composition。ToolExecutor 仍按工具名缓存 Provider，统一 create sandbox→provider.execute→terminate，使用旧 Grant/handle 接口；取消信号在结果后再次检查，不能证明候选的迟到成功保留规则。InProcessReadOnlySandbox 明确 osProcessIsolation=false、supportsForcedTermination=false。候选 Provider/Sandbox 分路、一次性 Permit、耐久证据、真实隔离/重启清理尚未在这些入口形成闭环。

仅作设计到现有入口的差异对照，未进行全仓安全审计，也未修改或删除上述实现。
