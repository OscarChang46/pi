# 安全判定、技术审批与一次性 Permit 草稿

> DRAFT · 待用户评审 · 2026-09-06
>
> 本文是非规范性提案，不批准或取代现行 candidate 文档，不修改契约签名及审批状态。
> 默认 local-first、单 Host；仅设计上层内核，Pi 核心与业务审批流程不在范围内。

## 问题与当前事实

同一动作在获得短时授权后，若两条并发请求都通过现有 Grant 复核，当前框架没有耐久的一次消费记录阻止重复执行。
需要把“允许这个动作”与“某个执行者已取得唯一执行资格”拆开，并记录崩溃后的证据。
一次消费只能限制执行资格，不能保证远程世界恰好产生一次副作用。

| 已核对事实 | 证据 | 尚缺能力 |
|---|---|---|
| 控制先调用 evaluate，再进入工具端口 | [ToolCoordinator](../../../../src/control/tool-coordinator.ts) | Ask 的持久化等待和恢复 |
| PermissionApprovalService 返回 Grant；人工确认要求直接拒绝 | [PermissionApprovalService](../../../../src/security/permission-approval.ts) | 技术审批桥接与 Permit 签发 |
| 工具层复核摘要、时效和停止状态 | [ToolRuntime](../../../../src/tools/tool-runtime.ts) | 耐久原子消费、重复调用收敛 |
| Kill Switch 是内存权威源 | [Kill Switch](../../../../src/security/kill-switch.ts) | 重启恢复、持久化撤销顺序 |
| 框架明确 Grant 不是 Permit | [框架映射](../../framework-boundaries.md) | 不可用改名代替协议迁移 |

设计依据：[BND-SEC-001](../../../design/contracts/bnd-sec-001.md)、[BND-L13-001](../../../design/contracts/bnd-l13-001.md)、[BND-OPS-001](../../../design/contracts/bnd-ops-001.md)。
组件依据：[PDP](../../../design/layers/security-plane/components/permission-decision-engine.md)、[Permit](../../../design/layers/security-plane/components/execution-permit.md)、[ApprovalBridge](../../../design/layers/security-plane/components/approval-bridge.md)、[PEP](../../../design/layers/security-plane/components/pep-enforcement.md)。

## 职责与数据所有权

| 组件 | 拥有 | 不拥有 |
|---|---|---|
| control 的权限协调点 | 不可变动作提案、恢复关联、等待原因 | 策略规则、Permit 消费记录 |
| security 的 PDP | 编译技术策略的判定、判定证据引用 | RBAC 权威库、Provider 调用 |
| security 的技术请求聚合 | 请求状态、动作摘要、截止时间、外部关联引用 | 业务 ApprovalCase、审批人选择、通知业务 |
| ApprovalBridge | 出站提交和回执映射、认证决定的入站适配 | 原始用户 Token、业务流程推进 |
| security 的 Permit 聚合 | 不变授权绑定、有效期、消费者、撤销及终态 | ToolCall 执行结果、执行重试 |
| tools 的 Guard | 实际执行与 Permit 绑定校验、请求原子消费 | PDP 规则、Ask/Allow/Deny、新 Permit |
| execution | 消费完成后的冻结计划执行与清理 | Permit 仓储、权限判定 |

各聚合通过 BND-INF-001 的仓储机制完成版本比较、状态及事件的同事务提交。
Run、技术请求、Permit、ToolCall 各自独立提交；传播通过耐久事件和幂等接收完成。
安全审计使用本地耐久事件事实再投递运维，不把远端审计后端纳入领域事务。
签发与消费的审计事实不能耐久提交时失败关闭。

## 正常流程

1. control 冻结动作、工具版本、目标、参数摘要、Run/Attempt、Agent、执行信封及策略上下文。
2. control 请求 PDP；PDP 在可信快照内完成唯一权限裁决，拒绝优先，不扩大调用方上限。
3. Deny 收敛为技术拒绝；Allow 在耐久记录完成后返回 Permit 引用。
4. Ask 先提交技术请求及待发送事件，再通知 Run 进入等待，释放认知执行槽和租约占用。
5. Bridge 异步提交同一技术请求；提交重试使用稳定请求标识，不能创建第二个审批流程。
6. Host 验证回调身份，Bridge 校验请求关联、动作摘要、策略上下文、截止时间及防重放证据。
7. 外部决定只是证据；control 恢复同一 PDP 决策流程，由 security 校验上下文仍有效后签发短时 Permit。
8. 原上下文失效时旧请求收敛为失效，control 创建新提案走新决策；不能复用旧人工 Allow。
9. control 将动作和 Permit 交给 tools；Guard 验证实际绑定和有效状态并原子消费。
10. 消费提交成功后，tools 才调用 execution；认知层从不接触 Permit。

“唯一裁决”指策略只在 control 请求的 PDP 流程执行；审批恢复属于该流程，工具守卫不再次计算规则。
撤销版本和紧急停止的强制检查属于执行有效性检查，不是一套新的策略裁决。

## 候选操作表

以下只有操作语义，不冻结完整 DTO、错误码或正式方法签名。

| 操作 / 边界 | 调用方 | 输入与输出语义 | 失败处理 |
|---|---|---|---|
| 请求判定 / BND-SEC-001 | control | 冻结提案、可信快照 → 拒绝、等待引用或 Permit 引用 | 不完整、超界、快照未知均拒绝 |
| 恢复审批判定 / BND-SEC-001 | control | 原请求、认证决定引用 → 收敛决定或短时 Permit | 失效上下文不可继承旧 Allow |
| 提交技术请求 / ApprovalBridge | 安全出站任务 | 稳定请求与脱敏摘要 → 外部关联回执 | 幂等重投、截止后停止 |
| 接收技术决定 / Host → Bridge | 认证通道 | 决定证据与关联 → 已记录或重复接收 | 伪造、迟到、摘要错配拒绝 |
| 查询/取消等待 / BND-SEC-001 | control | 作用域内请求引用 → 技术状态及版本 | 已终态不回退，未知引用不泄漏 |
| 校验并消费 / BND-SEC-001 | tools Guard | Permit 与实际动作及消费者 → 唯一消费回执 | 并发输家、过期、撤销、未知均不执行 |
| 查询消费事实 / BND-SEC-001 | tools 恢复器 | Permit 与 ToolCall 引用 → 耐久消费证据 | 查询成功不重新授予执行资格 |
| 撤销 / security 内部控制 | 可信管理入口 | 作用域及版本前提 → 新撤销事实 | 已消费保留事实，尝试停止后续动作 |

## 生命周期、事务与并发

技术请求候选状态：待提交、等待决定、已允许、已拒绝、已过期、已取消、上下文失效。
允许状态说明技术决定成立，不说明动作执行，也不说明 Permit 必然已经签发。
重复回调通过请求内决定标识去重；不同决定竞争时以条件提交获胜的有效决定为准。
冲突的第二个决定只留下拒绝接受证据，不覆盖第一次终结事实。
批准先提交但 Permit 尚未签发时，恢复器继续同一签发命令，保证签发意图幂等。
签发键按同一判定与动作绑定唯一；重复消息返回原 Permit，不生成额外并发有效 Permit。

Permit 候选状态：未消费、已消费、已撤销、已过期；终态不可恢复。
消费事务同时验证持久化绑定、有效期、版本前提和未消费状态，提交消费者及安全事件。
单 Host 的消费与撤销操作经同一安全写入序列执行，避免检查撤销后被抢先修改。
序列只覆盖安全状态短提交，不覆盖 Provider 请求，也不把 Run 和 ToolCall 纳入同一事务。
重启恢复完成前不开放消费；时间倒退或无法验证当前撤销状态时暂停受保护执行。
消费先于撤销成立时，撤销无法抹去消费事实；通过停止信号尽力阻断尚未发生的动作。
不能承诺撤销能回滚已经发生的网络或文件副作用。

Permit 已消费但 ToolCall 尚未落下后续状态，是允许存在且必须恢复的跨聚合窗口。
恢复器查询消费和 ToolCall 事实；无法证明尚未派发时进入 UNKNOWN_SIDE_EFFECT。
不把消费回执重放当成再次进入 execution 的授权；详见[工具执行草稿](tool-execution.md)。

## 安全与容量约束

- 默认单 Host 使用不可伪造的随机引用读取受信仓储中的 Permit；引用本身不是可移植离线凭证。
- 不允许不可信进程直接访问 Guard 或 execution；进程隔离通过 Host 边界与作用域身份落实。
- Grant 的当前摘要用于一致性检查，不能作为抗伪造签名；不直接将其升级为 Permit 证明。
- 技术请求、未消费 Permit、回调帧、外部摘要和出站队列均设置有限配额；超限明确拒绝新增。
- Permit 到期不得晚于动作 Deadline；默认短时窗口，审批等待不预先签发长寿命 Permit。
- 队列满或审计磁盘耗尽时关闭受保护动作准入，不静默丢弃安全事实。
- Secret、审批原文、用户凭证不进入摘要、日志或普通 Artifact；只保存必要证据引用。
- 操作按 Host 提供的可信租户/主体范围读取，跨范围查询和取消均拒绝。
- 终态保留期限至少覆盖最大重放及恢复窗口；删除前保留防重放墓碑或等价唯一性证据。

## 验收场景

1. 100 个消费者竞争同一 Permit，至多一个消费成功，Provider 至多获得一次初始派发。
2. 参数、路径目标、工具版本、Run 或信封变化后消费失败，Guard 没有调用 PDP。
3. Ask 等待期间运行槽可用于其他 Run，重启后恢复等待且外部重复提交不创建新请求。
4. 伪造、迟到、重复、相互冲突回调不能改变已终结请求，也不能增加 Permit 数量。
5. 审批期间策略版本变化时旧 Allow 不获得新动作执行权。
6. 消费提交超时后只查询事实；未知状态不触发 execution。
7. 审计不可用、仓储不可用、时钟回退和撤销状态未知均失败关闭。
8. 在技术允许与 Permit 签发之间崩溃，恢复后仍只有一个有效签发结果。
9. 在 Permit 消费与 ToolCall 后续提交之间崩溃，不恢复 Permit，不盲重试副作用。
10. 已消费后紧急停止不把既有动作标为未执行，取消结果保留真实副作用不确定性。

## 待用户评审决策

| 决策 | 默认提案 | 替代方案与取舍 |
|---|---|---|
| SEC-01 Permit 证明形式 | 单 Host 仓储引用与在线消费 | 签名凭证适合跨 Host，但仍需防重放仓储和密钥轮换 |
| SEC-02 审批接入 | Host 提供单一技术审批 Adapter，未装配则拒绝 Ask 能力 | 内置界面更易使用，但增加产品和身份边界 |
| SEC-03 版本变化 | 旧审批失效，重新提案 | 允许兼容版本映射可少打扰用户，但需另评审等价性证明 |
| SEC-04 消费不确定窗口 | 保守暂停并查询 | 可证明未派发后受控创建新调用更便利，但首版不自动化 |
| SEC-05 终态证据保留 | 与 Journal 保留和重放窗口统一配置 | 永久保存简化去重但增加隐私和空间成本 |

## 实施切片与跨域依赖

1. 先评审绑定语义和威胁边界，再为 Permit 仓储、技术请求、消费失败注入建立契约测试。
2. 接入本地耐久聚合提交及安全事件；将现有 Grant 路径整体切换到 Permit，禁止两条路径混用。
3. tools 增加原子消费守卫，与 ToolCall 恢复测试一并上线；execution 去除授权聚合访问。
4. 在 Scheduler 能释放/恢复等待槽后接入 Ask；无 Scheduler 支持时保持明确不支持。
5. 最后接入外部技术审批 Adapter、持久化撤销与安全审计导出。

需与存储草稿协调每聚合版本提交、签发唯一性、出站队列、审计耐久和墓碑保留。
需与调度草稿协调审批等待、截止时间、恢复信号与失效 Attempt 的处理。
需与 Host 草稿协调技术身份验证、管理权限、回调认证和通道限流。
